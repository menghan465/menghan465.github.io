从节点画布到 RPG Maker MV：DialogueFlow Studio 的数据分层、确定性编译与 Playtest 热刷新

对话系统最初可以直接写在 RPG Maker MV 的事件指令里，但当对话分支、变量修改和公共事件逐渐增多时，事件页就会变成一组难以审查的命令列表。这个问题不只是编辑体验差，还会影响版本管理、引用检查和运行时排错。 DialogueFlow Studio 是我为 Scelgrim 做的一个对话创作工具。它的目标不是替代 RPG Maker MV，也不是把所有剧情功能一次性做完，而是把“编辑对话”和“在游戏中运行对话”拆开，使两部分拥有比较明确的输入和输出。 先划分创作数据和运行数据 整个数据链路如下： content/dialogues/*.dialogue.json │ │ 校验、迁移、编译 ▼ data/dialogues/*.json + index.json │ │ RPG Maker MV 读取 ▼ Scelgrim_DialogueFlow.js content/dialogues/ 中保存的是创作文件。除了节点内容和连接关系，它还可以保留画布坐标以及以后可能增加的编辑器元数据。data/dialogues/ 中保存的是运行时文件，只保留运行协议需要的数据。这样做的原因是：画布坐标对游戏运行没有意义，却会污染运行时格式；如果两类数据混在一起，编辑器字段的变化也容易影响旧游戏版本。 运行时协议目前仍然是 v1，支持的节点类型只有六种：say、choice、branch、set、commonEvent 和 end。这不是功能缺陷被隐藏，而是有意限制协议范围。先保证节点含义稳定，比在运行时加入任意 JavaScript 或大量特殊节点更容易维护和验证。 编辑器真正需要解决的问题 节点画布本身并不难做，难点在于画布操作必须最终对应到一份可运行、可检查的数据。因此 Studio 目前把以下逻辑放在数据层，而不是只依赖界面状态： 节点拥有稳定 ID，连接保存为节点 ID，而不是数组下标； 重命名节点时同步更新引用，避免显示名称和实际目标不一致； 删除节点后检查是否产生悬空连接； 检查入口节点、不可达节点和不完整的分支； 导入旧版 v1 JSON 时，把 editor.positions 等编辑信息迁移到创作文件外壳中； 保存前通过 schema 校验，避免生成运行时无法解析的对象。 这类检查不能完全依赖用户肉眼观察。图形界面可以提示错误，但最终编译器仍然必须拒绝不满足协议的数据，否则问题会被推迟到玩家运行对话时才出现。 编译要可重复 构建命令会扫描整个 content/dialogues/ 目录，而不是只编译当前打开的文件。每份源文件先经过校验，再转换成运行时格式；随后工具扫描 data/dialogues/ 中已有的运行文件，重新生成完整的 index.json。 ...

在 RPG Maker MV 测试游戏中实现可视化图层编辑器：全地图相机、旋转缩放与动态公式

RPG Maker MV 的地图编辑器适合处理图块、事件和基础地图数据，但当地图中出现大量独立图片图层时，单靠参数和 JSON 很难继续维护。 我使用的 ULDS 图层系统会从地图 note 中读取多个 <ulds>JSON</ulds> 块，再把它们转换成 PIXI Sprite。一个图层可以配置图片路径、坐标、z 层级、透明度、旋转、缩放、混合模式、循环贴图和动态公式。 原始配置大致如下： { path: pictures, name: fog_01, x: this.rx(960), y: this.ry(720), z: 0.8, opacity: 180, scale.x: 1, scale.y: 1 } 这种格式可以运行，但存在几个直接影响制作效率的问题： 图片放置位置只能依靠手工填写坐标后反复测试； 图层数量增加后，很难判断同一 z 层级中有哪些对象； 图片旋转后，普通的水平和垂直缩放不再符合视觉方向； 动态公式能表达复杂行为，但不适合频繁手工编写； 修改最终仍要写回地图 JSON，需要避免覆盖外部修改或损坏地图文件。 因此我为 ULDS 增加了一个只在测试游戏中运行的可视化编辑器 ULDS_Editor.js。它不是 RPG Maker MV 自带编辑器的扩展窗口，也不是 Photoshop 的替代品，而是一个嵌入游戏运行时的地图图层制作工具。 最终实现的工作流是： 在 RPG Maker MV 中启动测试游戏； 按 F10 打开编辑器； 从素材栏选择图片并直接放到当前地图； 在游戏画面中拖动、旋转和缩放图片； 使用全局导航移动到玩家当前视野以外的位置； 编辑定位、裁切、动画帧和动态属性； 通过 Ctrl+S 把结果写回当前地图的 note。 本文讨论的重点不是界面样式，而是这个运行时编辑器需要解决的坐标、渲染、变换和数据持久化问题。 为什么把编辑器放进测试游戏 一种更常见的方案是制作独立网页或桌面客户端，读取 RPG Maker MV 项目目录并编辑地图文件。独立工具的架构更清晰，也更容易使用现代前端框架，但它很难完整复现游戏实际运行时的渲染状态。 ...

不重写 2D 玩法，如何在 Godot 中嵌入 3D 火车：SubViewport、坐标投影与屏幕空间碰撞

《黑猩猩与电车问题（The Chimpanzee and the Trolley Problem）》 是我为 GMTK Game Jam 2026 制作并提交的参赛项目。比赛提供了约 97 小时的提交窗口。本文讨论的技术方案属于截止时间前提交并锁定的版本，不是赛后重构。 它的规则层是一款三轨跑酷游戏：玩家控制电车换道，目标沿轨道接近，撞击后进入击飞状态；两分钟回合结束后，玩家可以在商店购买下一轮生效的道具。 在提交窗口内，项目进行过一次中途的视觉改造：玩法已经按 2D 坐标运行，我却希望把电车、轨道和沿线环境换成 3D，同时不重写现有的目标生成、碰撞、HUD 和回合逻辑。 我最后采用了一个混合方案： 3D 火车、轨道和环境放进 SubViewport； SubViewport 的纹理显示在 2D 主场景的 TextureRect 上； 猩猩、命中特效、HUD 和商店继续由 Node2D 管理； 通过 Camera3D.unproject_position() 把 3D 轨道位置投影回 2D 屏幕； 机车车头的 3D 投影再被转换成一个屏幕空间碰撞框。 这不是 3D 物理系统，也不是自定义渲染管线。它是一种面向 Game Jam 开发的范围控制：尽量保留已经能工作的规则层，只替换视觉层。 为什么不把整个游戏改成 3D 当时已经存在的 2D 系统包括： 三条轨道及换道逻辑； 目标生成与移动； 猩猩的 Sprite 动画和击飞效果； 手工命中判定； 两分钟回合、商店和三种道具； HUD、音频和最佳成绩存档。 如果全部改成 3D，就需要同时处理： 目标节点和运动方式重写； Area3D 或刚体碰撞重新标定； 3D 模型尺寸、相机 FOV 和玩法速度重新匹配； HUD 与世界对象的遮挡关系； 已经调好的 2D 击飞动画和商店流程回归测试。 对长期项目来说，全 3D 可能更统一；但在约 97 小时的提交窗口里，已有 2D 闭环能够运行时，全面重写带来的回归风险大于收益。这里的判断不是“混合架构永远优于全 3D”，而是“在剩余时间有限、现有规则已经可用的条件下，不应为了形式统一扩大改动范围”。我的目标不是建立一套通用框架，而是在不破坏现有闭环的前提下完成一次可控的视觉升级。 ...

RPG Maker MZ 可以通过 PixiJS Filter 使用自定义 fragment shader，但直接在插件中手写 GLSL 会带来两个问题：参数和表达式不容易复用，非图形程序员也很难快速调整效果。为验证“可视化编辑—实时预览—导出到 RPG Maker MZ”这条链路，我做了一个小型 2D Shader Graph 原型。 项目要验证的链路 项目的核心流程是： 节点图 JSON ↓ 节点类型与连接检查 ↓ GLSL ES 1.00 生成 ↓ PixiJS 预览 ↓ RPG Maker MZ 运行时插件 + .rmmzshader.json 编辑器使用 React 18、TypeScript、@xyflow/react 和 Vite。预览使用 RPG Maker MZ 所采用的 PixiJS 5.3.12。Shader 目标是 GLSL ES 1.00，因为这个版本更接近项目需要覆盖的 WebGL 运行环境。 节点图不是 shader 字符串 每个节点在图数据中拥有 ID、类型、位置、参数和输入连接。连接引用节点 ID 以及端口名，而不是引用数组下标。这样在移动节点、插入新节点或重新排列数据时，连接关系不会因为数组顺序变化而失效。 当前节点集合被限制在一个较小的子集：Texture、UV、Time、Float、Color、Add、Multiply、Sine、Mix、UV Warp 和 Fragment Output。它们足以验证纹理采样、时间动画、颜色运算和 UV 扰动，但不等于完整的材质编辑器。 ...

从课程项目到可验证系统：Spring Boot + Vue 家政服务平台的安全审计、本地 AI 与一键启动

这个家政服务系统不是我从零独立完成的项目。它的基础代码来自课程/团队项目，主要技术栈是 Spring Boot 2.5、Vue 2、MySQL、MyBatis 和 JWT。后续整理时，我没有把原系统重新包装成“个人独立开发”，而是针对现有代码做了审计、修复、配置整理和本地运行能力增强。 系统原本解决什么问题 系统包含用户、商品、服务类型、文件和后台管理等传统业务模块，前端使用 Vue 2，后端使用 Spring Boot 提供接口，数据库使用 MySQL。它的技术特点并不新，但适合用来观察一个传统全栈系统在安全性、可运行性和外部服务集成方面的问题。 这类项目的难点通常不在于写出一个 CRUD 页面，而在于让各层的约束保持一致：前端不能只负责隐藏按钮，后端也要重新校验角色；配置不能散落在源码中；上传文件不能因为拼接路径而越界；外部 AI 服务不可用时，主系统仍应给出可理解的错误状态。 本地 AI 的调用边界 我在系统右下角增加了一个只面向普通登录用户显示的本地 AI 助手。调用链路如下： 浏览器 ↓ Spring Boot /ai/chat ↓ LangChain4j 0.35.0 ↓ 127.0.0.1:11434 ↓ 本地 Ollama 模型 这里的“本地”不是一个宣传语，而是代码中的约束：服务端只接受 localhost、127.0.0.1 或 ::1 的 Ollama 地址，配置远程主机会拒绝启动；LangChain4j 的请求和响应日志关闭，聊天内容不会由本项目转发到云端模型。 前端助手只对角色为 USER 的已登录用户显示，后端 /ai/status 和 /ai/chat 仍会验证 token 与角色。最近对话只放在当前浏览器标签页的 sessionStorage，服务端不持久化聊天记录。接口还限制单条消息长度为 2000 个字符，最多接收最近 10 条历史消息，并设置本地模型调用超时与并发上限。 这个助手的边界也需要说清楚：它不能代替用户下单、付款、退款，也不能读取请求中没有提供的订单内容。它更接近一个受限的本地问答入口，而不是可以操作业务数据的智能客服代理。 本轮安全审计和修复 审计首先处理了不应该存在的启动授权逻辑。原代码会读取机器 UUID、请求第三方授权接口，并在授权失败时远程终止应用。我删除了这部分逻辑，避免系统在没有明确业务必要的情况下读取设备标识和依赖第三方控制。 ...
