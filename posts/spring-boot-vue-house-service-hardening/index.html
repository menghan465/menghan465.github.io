从课程项目到可验证系统：Spring Boot + Vue 家政服务平台的安全审计、本地 AI 与一键启动

记录一个基于课程/团队代码的家政服务系统如何经过安全审计、本地 Ollama 集成、配置整理、Windows 启动器和自动化验证，重点说明个人贡献范围与项目限制。
July 28, 2026

这个家政服务系统不是我从零独立完成的项目。它的基础代码来自课程/团队项目，主要技术栈是 Spring Boot 2.5、Vue 2、MySQL、MyBatis 和 JWT。后续整理时，我没有把原系统重新包装成“个人独立开发”，而是针对现有代码做了审计、修复、配置整理和本地运行能力增强。

系统原本解决什么问题#

系统包含用户、商品、服务类型、文件和后台管理等传统业务模块，前端使用 Vue 2，后端使用 Spring Boot 提供接口，数据库使用 MySQL。它的技术特点并不新，但适合用来观察一个传统全栈系统在安全性、可运行性和外部服务集成方面的问题。

这类项目的难点通常不在于写出一个 CRUD 页面，而在于让各层的约束保持一致：前端不能只负责隐藏按钮，后端也要重新校验角色；配置不能散落在源码中；上传文件不能因为拼接路径而越界；外部 AI 服务不可用时，主系统仍应给出可理解的错误状态。

本地 AI 的调用边界#

我在系统右下角增加了一个只面向普通登录用户显示的本地 AI 助手。调用链路如下：

浏览器
  ↓
Spring Boot /ai/chat
  ↓
LangChain4j 0.35.0
  ↓
127.0.0.1:11434
  ↓
本地 Ollama 模型

这里的“本地”不是一个宣传语，而是代码中的约束：服务端只接受 localhost、127.0.0.1 或 ::1 的 Ollama 地址，配置远程主机会拒绝启动；LangChain4j 的请求和响应日志关闭，聊天内容不会由本项目转发到云端模型。

前端助手只对角色为 USER 的已登录用户显示，后端 /ai/status 和 /ai/chat 仍会验证 token 与角色。最近对话只放在当前浏览器标签页的 sessionStorage，服务端不持久化聊天记录。接口还限制单条消息长度为 2000 个字符，最多接收最近 10 条历史消息，并设置本地模型调用超时与并发上限。

这个助手的边界也需要说清楚：它不能代替用户下单、付款、退款，也不能读取请求中没有提供的订单内容。它更接近一个受限的本地问答入口，而不是可以操作业务数据的智能客服代理。

本轮安全审计和修复#

审计首先处理了不应该存在的启动授权逻辑。原代码会读取机器 UUID、请求第三方授权接口，并在授权失败时远程终止应用。我删除了这部分逻辑，避免系统在没有明确业务必要的情况下读取设备标识和依赖第三方控制。

接口权限也进行了收紧。原来部分 /goods/**、/type/** 和 /files/** 路径被过宽放行；整理后只保留明确的只读接口，写操作要求有效 token。前端路由增加登录和角色守卫，但这只用于改善界面行为，真正的权限边界仍然放在后端。

账号处理改为 BCrypt 哈希。对已有的旧明文账号，系统在下一次成功登录时迁移为 BCrypt；登录响应不再序列化密码或新密码。这样做是兼顾已有课程数据和新密码存储方式的迁移方案，但生产系统仍应继续补充密码重置、登录失败限速、会话撤销和审计日志等能力。

其他修复包括：

  • 限制 CORS 来源，不再允许任意来源访问后端；
  • 修正生产环境中无效的 http://:9090 API 地址；
  • 修复匿名推荐时的空用户问题；
  • 替换无界线程池，并处理并发写入 ArrayList 的问题；
  • 修复文件路径越界风险，将文件保存位置统一到可配置的项目目录；
  • 消除重复前端路由名称，减少导航匹配不确定性。

这些修复并不等于完成了完整安全加固。它们只是针对已经发现、且能够在当前项目范围内验证的问题进行处理。

一键启动器解决环境问题#

原项目需要分别启动 MySQL、Spring Boot、Vue 和本地 Ollama。对熟悉项目结构的开发者来说这不算复杂，但对复现项目的人来说，遗漏任意一个进程都会表现为“页面打不开”或“AI 不可用”。

因此我增加了 Windows start.cmd 和 stop.cmd，启动顺序固定为：

  1. 查找本机 ollama.exe，必要时尝试安装；
  2. 启动绑定到 127.0.0.1:11434 的 Ollama；
  3. 检查并拉取默认的 qwen2.5:3b-instruct 模型；
  4. 检查并启动本机 MySQL 服务；
  5. 使用 Maven Wrapper 构建并启动 Spring Boot；
  6. 安装缺失的前端依赖并启动 Vue；
  7. 打开 http://localhost:8080/front/home。

模型可以通过命令行或 .env.local 切换。.env.local 被 .gitignore 排除，项目提供 .env.example 作为迁移模板，避免把当前机器的数据库密码提交到版本库。stop.cmd 只停止本项目启动的前后端进程，不主动停止 Ollama，因为其他本地程序可能仍然依赖它。

这个启动器的缺点也很明显：它依赖 Windows、MySQL 服务管理权限、Node/npm、Maven 下载源以及 Ollama 安装环境。它提升的是本地复现效率，不是跨平台部署方案。

数据库和接口边界#

项目增加了 springboot/src/main/resources/db/schema.sql，使用 CREATE TABLE IF NOT EXISTS 初始化必要表结构，不主动删除已有表或数据。数据库密码、JDBC 地址、文件目录、CORS 来源和 Ollama 参数都通过环境变量读取。

AI 相关接口目前只有两个主要入口：

方法路径作用
GET/ai/status检查本地 Ollama 和配置模型是否就绪
POST/ai/chat发送问题和最近对话历史

接口不直接暴露 Ollama 到浏览器，浏览器始终通过 Spring Boot 访问。这样可以集中处理身份验证、输入限制、超时和错误映射，也避免前端直接依赖本地模型服务的协议细节。

验证结果#

后端使用 Maven Wrapper 执行测试：

$env:JAVA_HOME='C:\Users\Administrator\.jdks\corretto-1.8.0_432'
.\mvnw.cmd test

结果为：

14 tests
0 failures
0 errors
1 skipped
BUILD SUCCESS

被跳过的是需要真实本地 Ollama 模型的冒烟测试。它不是普通单元测试失败，而是当前环境没有启用该外部依赖；如果要验证完整 AI 链路，需要显式设置 RUN_OLLAMA_TEST=true 并准备对应模型。

Vue 生产构建也成功，但构建工具报告图片、vendor 包和入口体积偏大的警告，另外 Browserslist 数据较旧。这些问题没有在本轮继续扩展处理，因为它们不影响当前安全审计和本地运行流程，但如果项目要部署到公网，应该进一步做资源压缩、按需加载和兼容性数据更新。

个人贡献和项目定位#

在作品集或简历中，这个项目应该写成“基于课程/团队基础项目进行安全审计和工程化增强”，而不是“独立完成家政服务平台”。可以明确列出以下个人工作：

  • 设计并实现本地 Ollama 的 AI 调用边界；
  • 处理鉴权、密码迁移、CORS、文件路径和并发相关问题；
  • 整理环境变量和 .env.example；
  • 增加数据库初始化脚本、Maven Wrapper 和 Windows 启停脚本；
  • 增加后端测试和本地运行说明；
  • 记录仍未解决的构建体积、外部服务和部署限制。

这种写法的可信度高于把传统课程项目描述成完整的个人 SaaS。它也更能说明我在接手已有代码后，如何定位问题、控制改动范围并用测试验证修改。

仍然缺少什么#

当前系统仍然没有云端部署、HTTPS、生产级数据库迁移、完整监控、集中日志、细粒度审计、完善的密码策略和跨平台启动方案的证据。AI 功能依赖本机 Ollama，不能直接据此声称具备稳定的在线模型服务能力。

因此，这个项目适合展示传统全栈开发和遗留系统改造能力，尤其适合说明“如何把一个能运行的课程系统整理成更容易复现、审计和维护的本地项目”。它的亮点不在技术栈新，而在于把安全边界、配置、外部服务和验证流程补齐到可以被检查的程度。
