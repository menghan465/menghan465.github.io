从节点画布到 RPG Maker MV：DialogueFlow Studio 的数据分层、确定性编译与 Playtest 热刷新

对话系统最初可以直接写在 RPG Maker MV 的事件指令里，但当对话分支、变量修改和公共事件逐渐增多时，事件页就会变成一组难以审查的命令列表。这个问题不只是编辑体验差，还会影响版本管理、引用检查和运行时排错。 DialogueFlow Studio 是我为 Scelgrim 做的一个对话创作工具。它的目标不是替代 RPG Maker MV，也不是把所有剧情功能一次性做完，而是把“编辑对话”和“在游戏中运行对话”拆开，使两部分拥有比较明确的输入和输出。 先划分创作数据和运行数据 整个数据链路如下： content/dialogues/*.dialogue.json │ │ 校验、迁移、编译 ▼ data/dialogues/*.json + index.json │ │ RPG Maker MV 读取 ▼ Scelgrim_DialogueFlow.js content/dialogues/ 中保存的是创作文件。除了节点内容和连接关系，它还可以保留画布坐标以及以后可能增加的编辑器元数据。data/dialogues/ 中保存的是运行时文件，只保留运行协议需要的数据。这样做的原因是：画布坐标对游戏运行没有意义，却会污染运行时格式；如果两类数据混在一起，编辑器字段的变化也容易影响旧游戏版本。 运行时协议目前仍然是 v1，支持的节点类型只有六种：say、choice、branch、set、commonEvent 和 end。这不是功能缺陷被隐藏，而是有意限制协议范围。先保证节点含义稳定，比在运行时加入任意 JavaScript 或大量特殊节点更容易维护和验证。 编辑器真正需要解决的问题 节点画布本身并不难做，难点在于画布操作必须最终对应到一份可运行、可检查的数据。因此 Studio 目前把以下逻辑放在数据层，而不是只依赖界面状态： 节点拥有稳定 ID，连接保存为节点 ID，而不是数组下标； 重命名节点时同步更新引用，避免显示名称和实际目标不一致； 删除节点后检查是否产生悬空连接； 检查入口节点、不可达节点和不完整的分支； 导入旧版 v1 JSON 时，把 editor.positions 等编辑信息迁移到创作文件外壳中； 保存前通过 schema 校验，避免生成运行时无法解析的对象。 这类检查不能完全依赖用户肉眼观察。图形界面可以提示错误，但最终编译器仍然必须拒绝不满足协议的数据，否则问题会被推迟到玩家运行对话时才出现。 编译要可重复 构建命令会扫描整个 content/dialogues/ 目录，而不是只编译当前打开的文件。每份源文件先经过校验，再转换成运行时格式；随后工具扫描 data/dialogues/ 中已有的运行文件，重新生成完整的 index.json。 ...
